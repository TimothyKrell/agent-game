## Pipeline

`.github/workflows/ci.yml` runs on pushes to `main`, open pull requests, and manual dispatch:

1. **Verify** installs the lockfile with dependency lifecycle scripts disabled, then runs lint (including warnings), formatting, all TypeScript checks, the production build, and a Worker bundle dry run. **Unit and Worker tests** distributes the entire existing Vitest inventory across three built-in shards, with one test worker per runner. **API and recovery tests** and **Browser and motion tests** run their complete suites on separate runners. Each job retains its 15-minute deadline.
2. **Verify production provider transport** runs the separate `npm run test:provider` suite against an isolated local HTTP Responses API. The actual Worker/HouseSeat/structured-provider path completes both Succession acts, validates accounting and stale-job fences, and exercises saved-response retry plus invalid-response/deadline interruption. Provider usage is synthetic; no paid model is invoked. Bash pipeline failure propagation preserves the test exit status while retaining the log.
3. **Deploy production** runs only after Verify, all three unit shards, API/recovery, browser/motion and provider verification pass for `main`. It deploys the existing `agent-game` / `prod` Alchemy stack and runs the public HTTP/OAuth-initiation/CLI/browser smoke check. The `production` GitHub environment is restricted to `main`.
4. **Build preview artifact** runs without deployment credentials in Verify for same-repository PRs. After the production client/CLI build, `scripts/produce-preview-artifact.ts` runs the locked Wrangler dry run with a local output directory. It packages the complete prebuilt Worker, static assets (including immutable CLI archives and rules), SQL migrations, and a canonical version-1 hash manifest. PR head and actual synthetic merge/build commit are distinct fields.
5. **Deliver trusted PR preview** is a separate default-branch `workflow_run` controller in `.github/workflows/preview-deploy.yml`, default-off until repository variable `TRUSTED_PREVIEW_DEPLOY_ENABLED=true` is set after credential cutover. It verifies the originating repository/event/workflow path/attempt, all seven required successful jobs, current open same-repository PR head, immutable tested-merge ancestry, and the exact run-scoped artifact ID/name/digest. The exact attempt's successful first Verify step records GitHub's original event merge/base/head; base-only advancement and full reruns retain that tested merge, independently of the moving PR merge ref. The CI workflow, setup action, producer and validator at the tested commit must match the controller checkout; the workflow at the associated PR head must match too. Changes to those files must land on the default branch before that producer can serve previews. No deployment job checks out or runs PR source, scripts, npm configuration, Alchemy, or plugins. ZIP download and bounded extraction happen outside the checkout before the Cloudflare secret step. The deployer supplies only a validated read-only byte snapshot to Alchemy `bundle: false` with exact module rules. It rechecks eligibility under the per-PR lock before writes and publication.

Preview URLs are `https://agent-game-pr-<number>.tk-d86.workers.dev`. They offer accelerated scripted exhibitions and terminal replays. Ratings are disabled; OAuth clients and paid inference bindings are omitted. Owner/account flows are covered by the local integration tests and the production smoke check.

`.github/workflows/preview-cleanup.yml` removes that PR's stack when it closes or merges and updates the comment. Cleanup uses the default branch's code and rechecks that the PR is still closed. It acknowledges retirement of the retained source incarnation before planning any target destruction, preserving retry identity on source failure. Alchemy destroys the retained stage inventory without needing the PR artifact, client build, or SQL migrations. This includes the private R2 picture bucket; preview deployments opt that bucket into removal of its temporary contents. Deploy and cleanup share `preview-<number>` concurrency with `cancel-in-progress: false`; production has its own serialized group. In-progress infrastructure writes finish before the next lifecycle operation.

## Credentials and configuration

Existing credential placement / required TIM-27 cutover:

- The existing repository-level `CLOUDFLARE_API_TOKEN` is account-scoped. Same-repository PR workflows can request repository secrets. Explicitly configure **both environments to allow only the default branch (`main`)**; GitHub silently creates an absent environment without protections. Preview delivery and cleanup require the **new environment-only** `TRUSTED_PREVIEW_CLOUDFLARE_API_TOKEN`; production keeps its existing secret name in the protected `production` environment. Remove the repository-scoped old token and any other PR-reachable broad Cloudflare credential, then enable repository variable `TRUSTED_PREVIEW_DEPLOY_ENABLED=true`. Missing/false activation prevents new deployment; a missing new secret fails before Alchemy starts, without fallback. Exact cutover steps are in [the delivery evidence](evidence/TIM-27-trusted-deploy.md#required-external-credential-cutover). No credential or environment-setting changes were performed here.
- The credential needs Workers Scripts, D1, private R2 bucket/object management, Secrets Store, and Account Settings access appropriate to Alchemy. Alchemy uses Secrets Store when authenticating its existing remote state store from a fresh runner. Local tests require none of these credentials.
- Source-bridge registration remains default-off pending cutover, an actual source release and protected `TRUSTED_PREVIEW_SOURCE_RELEASE` configuration. A source bridge cannot safely coexist with a broad Cloudflare edit token exposed to PR execution. Registration uses accepted default-branch functions through an atomic D1 REST adapter, with source/target database IDs from trusted Alchemy state; it has no public write route or target-provider credential. See [activation and broker handoff](evidence/TIM27-preview-lifecycle.md#broker-handoff-and-activation).

`production` environment secrets:

- `BETTER_AUTH_SECRET`
- `OAUTH_GITHUB_CLIENT_ID`, `OAUTH_GITHUB_CLIENT_SECRET`
- `OAUTH_GOOGLE_CLIENT_ID`, `OAUTH_GOOGLE_CLIENT_SECRET`
- `OPENAI_API_KEY` only if an OpenAI house provider is later selected

The `OAUTH_` prefix avoids GitHub's reserved `GITHUB_` secret-name prefix. Workflow steps map these names to the application's normal environment variables.

Repository variables:

- `CLOUDFLARE_ACCOUNT_ID`, `WORKERS_SUBDOMAIN`, `PRODUCTION_URL`
- `HOUSE_PROVIDER`, `HOUSE_MODEL`, `HOUSE_DAILY_BUDGET_USD`, `HOUSE_MATCH_RESERVATION_USD`, `MAX_CONCURRENT_MATCHES`
- Optional `HOUSE_SUCCESSION_MATCH_RESERVATION_USD`; an empty value uses `HOUSE_MATCH_RESERVATION_USD`.

GitHub supplies `GITHUB_TOKEN` for read-only repository/Actions verification and PR comments. Only the deployment/cleanup step receives the Cloudflare credential; dependency installation, quarantine and public smoke run without it. Trusted workflows install the default branch's lockfile with lifecycle scripts disabled and do not restore PR-shared caches. Alchemy reuses the account's remote state store. Local `.env.production`, `.dev.vars`, credentials, and generated deployment state are ignored by Git.

## Operations

- After trusted-delivery cutover/activation, open a PR to get a preview; its comment tracks the latest successful deployment.
- Merge into `main` to deploy production automatically after checks pass.
- For a PR preview, use **Re-run all jobs** after correcting a transient issue: every required job and the build artifact must belong to the same current attempt. A failed-jobs-only rerun with old successful jobs or an old artifact is deliberately ineligible. Manual **CI and deploy** dispatch on `main` still verifies and deploys production.
- Rotate the Cloudflare token in the default-branch-restricted deployment environments, using hidden terminal input. Do not restore a PR-accessible repository copy.
- Rotate application secrets through the `production` environment, then re-run production deployment.
- Closing a PR deletes its preview data. Production data remains in the `prod` stack.
- Cleanup remains enabled when new delivery is disabled. If a close run fails during cutover or an old stage remains, dispatch **Remove PR preview** on `main` with the canonical `pr-number`. The same protected new credential and live closed/same-repository PR check are required; there is no artifact dependency or legacy repository-secret fallback.

Pinned action revisions are maintained through weekly Dependabot PRs. npm dependencies remain governed by the existing lockfile and compatibility checks.
