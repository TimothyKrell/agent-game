## Bottom line

**Kody uses neither Better Auth nor Clerk.** Its browser authentication is application-owned code built with Remix cookie/router utilities, D1, password hashing, TOTP, and SimpleWebAuthn. Its inbound MCP authorization server uses **`@cloudflare/workers-oauth-provider`**, with additional application-owned consent and OIDC code.[^libraries][^mount][^password][^factors]

**Recommendation for Agent Game: use Better Auth for human Owner accounts, with D1-backed auth data, and an application-owned authorization layer that issues credentials bound to one stable Agent.** Reuse Kody's browser-versus-client credential separation, resumable onboarding, explicit consent, and connection management. Its MCP grant grants the client's user-wide assistant access; our required grant must instead identify one selected competitor. Kody is evidence for that separation on Workers, not evidence of a Better Auth deployment or a ready-made ranked-Agent identity model.[^grant][^connected]

This recommendation supersedes the earlier research note's *Clerk-first preference* for this discussion, given the user's preference to own auth through Better Auth. It does not claim Kent selected or recommended Better Auth.

### Route and framework boundary

The origin constructs `new OAuthProvider({...sharedOAuthProviderOptions, apiHandler, defaultHandler})`; its default handler ultimately dispatches to the Remix application. The app initializes cookie signing from Worker bindings and uses `router.fetch(request)`. Browser routes include `POST /auth`, `GET /auth/providers.json`, `POST /auth/:provider`, `GET /auth/:provider/callback`, `GET /session`, and `POST /logout`. This is not a mounted Better Auth `/api/auth/*` service.[^mount]

The Remix app router installs cross-origin protection. MCP/OAuth routes handled before it do not inherit that middleware. CORS also distinguishes browser app requests from `/mcp`: the latter permits remote browser MCP hosts to send bearer-token requests and exposes `WWW-Authenticate`. This is a useful reason to design each HTTP boundary explicitly rather than assume one framework middleware covers everything.[^origins]

## 2. Human authentication and account lifecycle

### Signup, login, session, logout

- **Password UI:** one login/signup component posts JSON to `/auth`. Signup includes a username; login offers remember-me. It also renders configured social providers and a passkey login action. Redirect selection preserves the original safe `redirectTo`, including through the pending-email-verification and TOTP pages.[^client]
- **Password server:** normalizes email, verifies or creates the user in D1, assigns the user role, and issues a signed cookie. Password hashing is custom Web Crypto **PBKDF2-SHA256, 100,000 iterations**, with random salts and hash-upgrade support. This is Kody's algorithm, not a Better Auth default.[^password]
- **Signup completion:** password signup creates email verification before issuing its session; failure to set up verification removes the new user so signup can be retried. The verification pipeline uses Cloudflare's email API, with a non-production exception when sending is unconfigured. Verified email is required before MCP authorization completes, while an unverified user can hold a browser session.[^signup]
- **Cookie:** `kody_session`, `HttpOnly`, `SameSite=Lax`, `Path=/`, signed with `COOKIE_SECRET`; no cross-domain `Domain` is configured. Payload is version 2 with `stableUserId`, email, `issuedAt`, and optional remember-me. Ordinary sessions last seven days; remembered sessions thirty days, renewed after fourteen days. `Secure` is decided from forwarded protocol headers or the request URL.[^cookie]
- **Normal protected-page resolution:** cookie parsing is followed by a live D1 user/roles lookup, absolute-expiry checks, password-change invalidation, and deletion/suspension checks. A `WeakMap<Request, Promise<...>>` deduplicates work within one request, rather than caching authorization between requests.[^resolution]
- **Logout:** the account UI submits `POST /logout`; the handler expires this browser's cookie and redirects to `/login`. It does not revoke MCP grants or maintain a per-session server-side revocation record.[^logout]

### Social login: four real implementations, conditionally enabled

| Provider | Requested login scopes | Identity resolution |
| --- | --- | --- |
| GitHub | `read:user user:email` | GitHub user ID; primary verified email from `/user/emails`, with unverified public-email fallback. |
| Google | `openid email profile` | `sub` and `email_verified` from OIDC userinfo. |
| X | `tweet.read users.read users.email` | May lack verified email; then only an existing link or authenticated linking can work. |
| Discord | `identify email guilds.join` | Discord ID and verified email; callback also best-effort joins the official guild and syncs configured roles. |

These definitions and handlers are built. Whether each is active in production depends on secrets: both client ID and secret must be configured to expose its button. `MOCK_` client IDs activate mock login only in non-production. Social-login provider access tokens are used for the profile fetch and, for Discord, the guild join; this identity table does not persist them. Outbound assistant API integrations are a separate OAuth subsystem.[^providers][^linking]

Social login starts with a same-origin JSON POST, then client-side top-level navigation to the returned provider URL. A signed `kody_oauth_login` cookie carries provider, state, PKCE verifier, and the return path; the callback checks state/provider/code and clears the cookie. Its browser max-age is ten minutes. Google/X/Discord enable S256 PKCE; **GitHub explicitly disables it in this snapshot**.[^social-flow][^providers]

### Linking and durable identity

The callback's actual order is:

1. A signed-in account with a live verified email links the provider; a provider already linked to another user is a conflict.
2. An existing provider connection logs in its user.
3. A verified provider email matching an existing email **implicitly links** to that account. If the existing account was unverified, Kody first replaces its password with an unusable sentinel, invalidates older credentials, and clears second factors and connections.
4. Otherwise, a verified provider email creates a new account, with a generated username and no usable password, then continues to onboarding or the preserved destination.[^linking]

Disconnecting a provider uses a conditional SQL `DELETE` that requires another usable sign-in method to remain; the check and removal occur in the same statement.[^unlink]

Kody has a numeric D1 `users.id` and an authoritative stored `stable_user_id`. New identities normally start as SHA-256 of normalized signup email, but later email changes must not recompute them. There is also a random-ID fallback when a released email's hash is still held by another account. **Reuse identity stability, not the email-hash allocation rule:** Agent Game should allocate independent opaque Owner and Agent IDs, preserving them through provider linking, renames, and credential rotation.[^identity]

### Second factors, recovery, deletion

- TOTP setup/verification is built on `@epic-web/totp`. Password and social login for a 2FA-enabled account issue a short-lived `kody_verify` cookie instead of the real session. Passkey registration requires an existing authenticated account; successful passkey login requires WebAuthn user verification and deliberately skips TOTP. RP ID/origin derive from the request host.[^factors]
- Password reset/change coordinates OAuth grant revocation and `password_changed_at`. Reset can clear TOTP, passkeys, and linked providers; signed-in password change preserves those factors. Normal protected-page resolution and MCP token checks consult the timestamp.[^recovery][^resolution]
- Account deletion requires a resolved user, the phrase `GOODBYE KODY`, and the current password when the account has a usable password. Cleanup is application orchestration across external resources, OAuth grants/clients, DOs, and D1. Failures keep the account available for a deletion retry; the final D1 cleanup removes the user after preceding cleanup succeeds. This cannot be replaced by deleting an auth-library user row if the application has game history and Agent grants.[^deletion]

### Relevant configuration names

Source names, without secret values:

- Browser identity: `COOKIE_SECRET`, `APP_BASE_URL`, `APP_LEGACY_HOSTS`, `APP_LEGACY_REDIRECT`; `APP_DB` D1 binding.
- Social login: `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET`, `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`, `X_CLIENT_ID` / `X_CLIENT_SECRET`, `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET`.
- MCP/OIDC: `OAUTH_KV`, provider-injected `OAUTH_PROVIDER`, `OIDC_SIGNING_PRIVATE_KEY_PEM`, `OIDC_SIGNING_KEY_ID`.
- Supporting flows: `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`; verification-mail `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_API_BASE_URL`, `SYSTEM_EMAIL_DOMAIN`. Discord guild/role configuration is optional and product-specific.[^cookie][^providers][^environment][^signup]

Social callbacks use the initiating canonical/explicitly allowed legacy host where possible, preserving host-scoped state cookies; other hosts fall back to `APP_BASE_URL`. Application return paths must be same-origin absolute paths, rejecting protocol-relative URLs, backslashes, and control characters.[^social-flow][^redirect]

## 3. External agents, CLI, and credentials

**Kody already supports agent-initiated browser authorization.** Public `/auth.md` advertises discovery, client registration, authorization-code/refresh-token grants, and the `/mcp` resource. The host opens OAuth; the person signs in and approves. Onboarding includes generated setup instructions for Claude Code, OpenCode, other MCP hosts, and `npx @kodycodes/cli install`. Those are setup instructions in Kody, not proof that the external clients were tested in this research.[^discovery][^cli]

The important boundary is visible in code:

```text
Kody:
  person → browser login → Kody user session
  MCP host → /oauth/authorize → person approves
           → provider issues bearer/refresh credential for that USER
           → /mcp resolves the user's assistant

Agent Game — proposal:
  person → Better Auth → Owner session
  harness → pending connection → Owner signs in
          → select/create stable Agent → approve
          → game issues credential for that AGENT
          → game actions resolve Agent principal and permitted actions
```

Kody's consent UI literally says **“This agent gets full access.”** The granted props contain user ID, email, username, display name, and auth time. `/mcp` validates the bearer and audience, resolves live user identity, checks verification/suspension/password-change state, and supplies that user's context to MCP. OIDC scopes `openid`, `profile`, and `email` do not restrict assistant capabilities; ADR 0049 explicitly chooses full-assistant grants.[^grant][^mcp]

Its “connected agents” are grants grouped by OAuth **`clientId`**, labeled from host/client metadata and revocable by connection. Its onboarding “selected agent” is a browser-session preference identifying a **host kind**, such as Claude Code. Neither is a persistent named competitor with independent standings. One software client ID must not become our ranked `agentId`.[^connected]

### Protocol/storage specifics

- Provider routes are `/oauth/authorize`, `/oauth/token`, and `/oauth/register`; CIMD is enabled. The official CLI's metadata declares a public native client (`token_endpoint_auth_method: none`), authorization-code/refresh grants, and `http://127.0.0.1:43742/callback`. Its implementation resides in a separate repository linked by that metadata; only Kody's server-side support was inspected here.[^oauth-options][^cli]
- Access-token lifetime is the provider's **one-hour default**. Kody deliberately sets `refreshTokenTTL: undefined` and `clientRegistrationTTL: undefined`, overriding thirty-day and ninety-day library defaults to remove those expiries. Omitting those options would retain the defaults. The pinned dependency source confirms the defaults and option-spread behavior.[^oauth-options][^provider-defaults]
- OAuth data uses **Workers KV**. The actual pinned provider reads access-token records from `OAUTH_KV` in `unwrapToken`; its `revokeGrant` deletes associated access-token records and then the grant. These are not self-contained JWT access tokens. Kody separately enriches responses with an OIDC `id_token` when `openid` is granted.[^provider-storage][^oidc]
- **No device-code grant/polling flow was found** in the checked Kody application source. Its advertised grants are authorization-code and refresh-token. Opening a browser from an agent is not by itself RFC 8628 device authorization.[^discovery][^cli]
- There is a separate **package-invocation bearer-token** path with hashed secrets and package/export scope, plus account-side token actions. It is still wired, but ADR 0048 makes it an **unadvertised retirement/drain path**, favoring package-owned webhooks. It is not Kody's standard MCP onboarding mechanism and not evidence of an Agent-profile API-key system.[^invocation]

### Database placement

Auth/account tables live in `APP_DB` D1: `users`, password-reset and email-verification records, `oauth_connections`, `verifications` for TOTP, and `passkeys`. Provider identity has a unique `(provider_name, provider_id)` constraint. Committed SQL migrations, including the initial squashed schema and subsequent user-table rebuild, define this schema. The custom D1 adapter uses the D1 API; DO SQLite is not its backing adapter. OAuth grant/token/client data is in KV rather than the browser-account schema.[^database][^migrations][^runtime][^provider-storage]

## 4. Source contradictions and defaults worth noticing

These qualify reuse; they are not a completed security audit.

1. **Stale GitHub PKCE comment:** Kody says GitHub OAuth apps ignore PKCE and sets `usesPkce: false`. GitHub's current official OAuth-app documentation supports and recommends `code_challenge`/`code_verifier` with S256. Report what Kody does, but do not inherit that rationale as an upstream limitation.[^providers][^github]
2. **Browser sessions versus access tokens:** Kody's browser cookie is stateless as a credential format, but authorization still consults D1. Its MCP code calls access tokens “stateless” and says they cannot be individually revoked, while the actual installed provider uses KV-backed token records and deletes them on grant revocation. Describe those storage operations rather than repeat the comment or promise globally instantaneous revocation.[^cookie][^resolution][^mcp][^provider-storage]
3. **Cookie parsing is not full session resolution:** `readAuthSessionResult` only parses/possibly renews the signed cookie. Normal protected pages use the stronger `loadResolvedRequestAuth` path. Social-linking callbacks and OAuth authorization use lower-level cookie readers with their own checks; the OIDC gate's age check is conditional on a requested `max_age`, not the normal absolute cookie-expiry check. Centralizing complete Owner-session resolution is a better reuse pattern than copying all these distinct paths. This is a source-level consistency finding, not an exercised exploit.[^resolution][^reader-divergence]
4. **Documentation can lag code:** the architecture document lists `POST /session` and claims password changes cannot invalidate older cookie sessions; source routes/client use **GET**, and the main session resolver does check `password_changed_at`. Similarly, comments saying passkey login waits for TOTP conflict with the explicit MFA-complete passkey handler.[^doc-drift][^mount][^client][^resolution][^factors]

## 5. Concrete Better Auth recommendation for our stack

### Reuse the product patterns

**Proposal:** public discovery and harness instructions → resumable sign-in/signup → one approval screen → connection status and revoke/reconnect management. Preserve the pending connection across login, account creation, and any verification; reconnect to an existing Agent by default rather than create a new leaderboard identity accidentally. Show the Owner, selected Agent, requested play permissions, and installation label before issuance. These extend Kody's resumable consent and connected-client patterns to our domain.[^redirect][^discovery][^connected]

### Use Better Auth for Owner authentication

**Proposal:** start with GitHub and Google social login, using `better-auth/react` in React/Vite and a standard Worker `Request`/`Response` handler at `/api/auth/*`. Resolve a validated Better Auth user/session to an application Owner ID at the backend boundary. Translate that result into the pinned Effect 4 RC application's services; use Alchemy 2 beta for provisioning bindings/secrets. This is an architectural boundary proposal, not a verified version-specific Effect/Alchemy adapter.[^ba-install]

**Proposal:** give Better Auth its own D1 database/schema and retain SQLite-backed DOs for game coordination and whichever Agent/grant state the application assigns to them. Better Auth's first-party documentation establishes native D1 support by passing a D1 binding directly. Cloudflare describes D1 and DO SQL as different interfaces: DO SQL is private to an object and accessed through `ctx.storage.sql`. No official drop-in Better Auth adapter for that interface was established here. Using only DO storage for authentication would require a separate adapter/storage investigation.[^ba-d1][^cf-do]

**Proposal:** prefer database-backed Owner sessions, with cookie caching disabled initially so management requests consult current session state. Better Auth supports session listing/revocation; its optional cookie cache can delay observing revocation. Set the canonical base URL, allowed origins, HTTPS cookie behavior, and provider callbacks explicitly per environment. Better Auth already supplies state/PKCE and origin/redirect protections; implement our application approval authorization around them.[^ba-session][^ba-cookie][^ba-security]

Better Auth requires AsyncLocalStorage support. Kody's earlier compatibility date uses `nodejs_compat`; current Cloudflare docs say Node compatibility is default on dates **2026-08-04 onward**. Choose settings for our actual compatibility date instead of copying Kody's or an older example blindly.[^ba-install][^cf-node]

**Account-policy difference:** Kody implicitly links verified same-email social identities and implements unverified-account reclamation itself. Better Auth also documents implicit linking by default, but supports **`disableImplicitLinking: true`** with authenticated `linkSocial()` still available. **Proposal:** use explicit authenticated linking initially, decide recovery deliberately, and preserve at least one sign-in method. Better Auth exposes deletion hooks, but Agent Game must own revoking Agent grants and preserving/retiring attributable match history.[^linking][^unlink][^ba-accounts]

### Issue Agent-scoped credentials after approval

**Recommended initial proposal:** implement an application-owned pending connection/pairing service. The harness requests a connection and retains its private retrieval credential; the Owner opens the game's URL, authenticates with Better Auth, selects/creates an Agent, and approves. An authoritative state transition binds the request and issued grant to **one `agentId`**. The originating harness retrieves a random opaque game credential; store a verifier and grant metadata server-side, with explicit expiration and revocation. Game requests derive the Agent from that grant, not from a freely supplied Agent ID or the Owner session. Keep credential replacement separate from ranked identity.

This directly serves generic outbound-HTTPS harnesses, including remote environments without a browser callback listener. If adopting RFC 8628 wire semantics, implement its code expiry, polling interval, denial, and `slow_down` behavior. The protocol and Better Auth's documented flow supply browser pairing mechanics; Agent selection and grant policy remain ours.[^ba-device]

**Important Better Auth distinction:** standalone `deviceAuthorization()` finishes with a **Better Auth session token**, even though its JSON calls it `access_token`. It should not be handed to a play-only harness as an Owner management credential. Better Auth's documented OAuth composition instead uses `jwt()`, `oauthProvider()`, and `oauthDeviceAuthorization()` from `@better-auth/oauth-provider`, polling `/oauth2/token` for scoped, audience-bound OAuth tokens. That is the path to evaluate if standards-based OAuth/MCP interoperability is a day-one requirement. It still needs an application-enforced, immutable Agent binding across approval, issuance, refresh, and game actions; `api:play` alone does not choose one of an Owner's several Agents.[^ba-device]

**Suitability judgment:** Better Auth is suitable for the stated Owner-account needs and Workers/React boundary, provided D1 auth storage is acceptable. Kody demonstrates how much bespoke account lifecycle code its own approach entails; it gives no reason to reproduce that entire auth implementation for this game. Choose an exact Better Auth/core/plugin release set during implementation: the current docs and the historical 1.5 announcement must not be mixed into an assumed single-version API contract.[^ba-install][^ba-d1][^ba-device]

## Decisions still needed

1. **Accept D1 for Owner auth**, or insist on DO-only storage and investigate the adapter first?
2. **Confirm initial login/recovery policy:** GitHub + Google, explicit linking, and whether password/passkey enrollment is needed at launch.
3. **Connection protocol:** application pairing for generic harnesses, or OAuth/MCP-native clients from day one? This determines whether to use Better Auth's OAuth Provider machinery immediately.
4. **Delegation policy:** one match, a bounded period, or ongoing installation access; credential expiry/renewal; revocation effect on active matches; concurrent installations per Agent.
5. **Account/Agent lifecycle:** deletion and retirement, preservation of historical standings, and whether ownership transfer is allowed. Better Auth account deletion must coordinate with these rules.
